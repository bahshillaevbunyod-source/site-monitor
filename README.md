# Монитор сайтов с Telegram-ботом

## Что это
Программа, которая раз в час заходит на мои сайты как обычный посетитель и проверяет, что они открываются. Если сайт сломался, она пишет мне в Telegram. Когда сайт ожил, пишет «снова работает».

Аналогия: сторож обходит магазины и звонит хозяину, если дверь закрыта. Один раз не открыли: может, отошли, молчит. Не открыли дважды подряд: звонит. Потом не звонит каждый час, а ждёт, пока откроют, и звонит ещё раз.

Монитор только ЧИТАЕТ: один запрос GET на главную страницу. Ничего не отправляет и не меняет на сайтах.

## Как устроено

```
sites.json ──► проверка ──► правило «сбой» ──► Telegram
(список)      (check-core)   (decide)           (telegram.mjs)
                                 ▲
                      Cloudflare KV (память)
Всё запускает Cloudflare Worker по расписанию (Cron Trigger).
```

| Файл | Что делает |
|---|---|
| `sites.json` | Список сайтов: название, адрес, ключевой текст. Добавить сайт можно, не трогая код. |
| `lib/check-core.mjs` | Проверяет один сайт: код ответа (нужен 200–299), время (дольше 3 с — «медленно», дольше 10 с — нет ответа), есть ли на странице ключевой текст. |
| `lib/decide.mjs` | Правило «сбой». Чистая функция без зависимостей, её легко тестировать. |
| `worker/index.mjs` | Cloudflare Worker: проверяет все сайты одновременно, применяет правило, шлёт сообщения, пишет состояние в KV. |
| `wrangler.toml` | Настройки Worker: расписание, привязка к KV. |
| `telegram.mjs` | Отправка сообщения через Telegram Bot API. |
| `messages.mjs` | Тексты сообщений. Правятся отдельно от логики. |
| `monitor.mjs`, `check.mjs` | Версия для запуска вручную в Node (на компьютере). |
| `.github/workflows/monitor.yml` | Резервный запуск в GitHub Actions только по кнопке. Расписание отключено (см. ниже). |

## Правило «сбой»
- Плохая проверка: код не 2xx, нет ответа за 10 с, ошибка соединения или нет ключевого текста.
- **2 плохих проверки подряд** → сообщение «не работает» (один раз).
- Первая хорошая проверка после этого → сообщение «снова работает».
- Одна случайная заминка между хорошими проверками сообщения не вызывает.
- Если Telegram не принял сообщение, состояние откатывается и отправка повторяется при следующем запуске. Тревога не теряется.
- Медленный ответ пока только помечается, в Telegram не пишет.

## Где что живёт
| Место | Что там |
|---|---|
| Компьютер (`C:\site-monitor`) | Разработка, `.env.local` с токеном (только здесь) |
| GitHub | Хранилище кода и его истории. Сайт и монитор не запускает |
| Cloudflare Worker `site-monitor` | Здесь работает монитор, раз в час в :07 UTC |
| Cloudflare KV | Память монитора: состояние сайтов и отметка последнего запуска |
| Telegram | Куда приходят сообщения |

Состояние нужно, потому что Worker включается на пару секунд и выключается, переменные пропадают. Без памяти счётчик «два подряд» обнулялся бы каждый час, и тревога не сработала бы никогда.

## Секреты
`TELEGRAM_BOT_TOKEN` и `TELEGRAM_CHAT_ID` лежат в `.env.local` на компьютере (в git не попадает) и в секретах Cloudflare Worker. В коде и в репозитории их нет. Репозиторий публичный, поэтому это важно. Если токен утечёт: выпустить новый в @BotFather (`/revoke`) и обновить в обоих местах.

## Как проверено
- Проверка на живых сайтах и на заведомо сломанных: 404, неверный текст, несуществующий адрес.
- Тест правила на 11 шагах (случайная заминка, оживление после падения).
- Имитация сбоя отправки в Telegram: сообщение не ушло, состояние откатилось, при следующем запуске ушло, повторно не дублируется.
- **В Cloudflare:** тестовый адрес (файл в репозитории) удалён → после двух плохих проверок пришло 🔴 → файл возвращён → пришло 🟢. Оба сообщения отправил Worker, я увидел их в Telegram сам.
- Первый обход по расписанию Cloudflare пришёлся на 06:07:27 UTC при расписании «:07».

## Почему не GitHub Actions
Сначала запуск был в GitHub Actions по расписанию. Я измерил: за 12 часов вместо ~12 запусков по расписанию прошло 2 (в 23:02 и 03:53 UTC, дыра почти 5 часов). GitHub не гарантирует точность расписаний. Поэтому запуск перенесён в Cloudflare Workers: у них расписание точное и бесплатно. Таймер в GitHub отключён, чтобы не было двух мониторов с разной памятью.

Vercel Cron не подошёл: на бесплатном плане расписания не чаще раза в 15 минут (по документации Vercel).

## Чего не проверено и ограничения
- Цепочка запусков раз в час за долгое время (сутки и дольше) пока не наблюдалась. Проверяются несколько часов подряд.
- Изменение расписания в Cloudflare применяется с задержкой (в моей пробе около 10 минут).
- Выкладка в Cloudflare делается вручную командой `npx wrangler deploy`: автоматической выкладки из GitHub нет.
- Таймаут 10 секунд отдельным тестом не проверялся.
- Сайт `kofe-nuqta.vercel.app` отвечает 404 и числится «упавшим»: оставлен намеренно.
- Проверяется только главная страница, не вся работа сайта (формы, оплата, вход не проверяются).
- Aevum отвечает медленно (3–5 с): пока только пометка.

## Почему такие решения (для собеседования)
- **Раз в час и порог 2:** раз в день — узнаёшь о падении почти через сутки; раз в 5 минут — лишняя нагрузка. Час с порогом 2 даёт обнаружение за 1–2 часа почти без ложных тревог. Цена: на час позже.
- **KV для состояния:** Worker запускается на секунды и забывает всё, поэтому память хранится снаружи.
- **Общий код без зависимостей от Node (`lib/`):** одну и ту же логику запускают и Worker, и локальный скрипт.
- **Список сайтов отдельным файлом:** чтобы добавлять сайты, не трогая код.

## Запуск вручную
```
node --use-system-ca --env-file=.env.local monitor.mjs
```
Выкладка Worker: `npx wrangler deploy` (нужен вход `npx wrangler login`).
